**Title:** Hardware codecs, SVC, and why your settings kept disappearing\
**Date:** 2 March 2026\
**Author:** Sivert Gullberg Hansen\
**Keywords:** WebRTC, H.264, AV1, scalable video coding, SFU, Electron, localStorage

## Abstract

Three changes shipped within days of each other. Screen sharing used whatever codec
the browser picked, usually VP9, which consumer GPUs almost never encode in hardware,
so the CPU did all the work. It now prefers H.264, which the GPU encodes, and lets
you pick AV1 or VP9 instead. Second, the SFU used to send every viewer the same
packets, so one viewer on a bad connection set off keyframe requests that hurt
everyone. With three temporal layers in one stream, it now sends each viewer 7.5, 15
or 30 fps depending on their bandwidth. Third, the desktop app sometimes lost every
setting and sign-in between restarts, because Electron's `localStorage` is tied to an
origin that can change. Every entry is now backed by a file in the userData
directory, without touching the code that reads and writes it.

## 1 Introduction

This post answers three questions:

1. **Why did screen sharing load the CPU so much**, and how do we get it onto the GPU?
2. **How can one stream serve viewers on very different connections** without the
   worst one dragging down the rest?
3. **Why did the desktop app lose its data between restarts?**

## 2 Background

### 2.1 Codecs and hardware

When Gryt first got screen sharing, it used whatever codec the browser picked. That
usually meant VP9. It's a fine codec and it compresses well, but consumer GPUs almost
never hardware-encode it, so your CPU was doing all the work. Share a game at 1080p
30fps and you could feel it.

WebRTC lets you tell the browser which codec you'd rather have, with
`setCodecPreferences` on the transceiver [1]. Put H.264 first and the browser
negotiates H.264 and hands the encoding to your GPU: NVENC on NVIDIA, Quick Sync on
Intel, AMF on AMD.

### 2.2 Scalable video coding

Scalable Video Coding [2] lets the encoder produce temporal layers within a single
stream. With L1T3, the encoder outputs three frame rate tiers in one RTP stream. A
receiver can drop the upper layers and still decode clean frames at a lower rate.

### 2.3 Storage in Electron

The desktop app stores authentication tokens, theme settings, server configurations
and other preferences in `localStorage`. In Electron that storage is origin-bound,
tied to the specific `http://127.0.0.1:port` URL the app loads. If that port changes,
or the Chromium profile gets reset, or storage is cleared during an update,
everything is gone.

## 3 Design

### 3.1 Codec selection

Table 1 has the codecs you can pick from. Auto checks what your browser supports
with `RTCRtpSender.getCapabilities("video")` and goes for H.264, because everything
can play it. If you know your hardware does AV1, switch to it and get better quality
for the same bandwidth.

**Table 1:** The codecs on offer.

| Choice | What it does |
|---|---|
| Auto | H.264 if the browser supports it |
| H.264 | Hardware-encoded on nearly every GPU, plays everywhere |
| VP9 | Compresses well, but almost always encoded on the CPU |
| AV1 | Compresses a lot better at the same bitrate; hardware-encoded on RTX 40 series, Intel Arc and AMD RX 7000+ |

One codec isn't on the list: H.265/HEVC. It's everywhere in video streaming, but
WebRTC doesn't support it and the browser APIs won't let you negotiate it. AV1 does
the same job with better compression, in browsers that actually support it.

All of this sits behind an "Advanced" toggle in the screen share dialog. The defaults
are good, so most people never open it. But if you want to change the codec, the
bitrate or the degradation preference, it's there.

### 3.2 Gaming mode

Alongside the codec work, I added a "Gaming mode" toggle, on by default, that bundles
the encoder hints in Table 2 for fast-moving content. For a presentation or anything
text-heavy, turn it off and it goes back to resolution first.

**Table 2:** What gaming mode sets.

| Setting | Value | Why |
|---|---|---|
| Cursor | Stripped from the capture | Nobody watching sees a frozen cursor over a game that hides it |
| Content hint | `motion` instead of `detail` | Tells the encoder to keep the frame rate up rather than the sharpness |
| Degradation preference | `maintain-framerate` | WebRTC drops resolution before frame rate when bandwidth is tight |
| Bitrate | 1.5x the estimate, capped at 20 Mbps | Gives the encoder more headroom |

### 3.3 Layer-aware forwarding in the SFU

Figure 1 shows one L1T3 stream going out to three viewers. The SFU parses the
Dependency Descriptor RTP header extension [3] on each incoming packet to find out
which temporal layer it belongs to. For each receiver, it decides how many layers to
forward based on that receiver's available bandwidth, read from its REMB feedback [4].
Table 3 has the thresholds.

**Figure 1:** One stream, three viewers. The SFU forwards each one only the layers its
bandwidth can take.

**Table 3:** Layers forwarded by the viewer's estimated bandwidth.

| Viewer's bandwidth | Layers | Frame rate |
|---|---|---|
| Below 1 Mbps | T0 | 7.5 fps |
| Below 3 Mbps | T0 + T1 | 15 fps |
| Above 3 Mbps | T0 + T1 + T2 | 30 fps |

Before SVC, the SFU did blind byte-copy relay, so every receiver got identical packets
regardless of their bandwidth. A viewer with a bad connection got packet loss, which
triggers PLI (Picture Loss Indication) requests back to the sender, which forces
keyframes, which hurts quality for everyone. With SVC, constrained viewers just get
fewer temporal layers. Clean frames, no packet loss storms, no impact on other
viewers.

There's also a `set_layer` WebSocket event for manual control, which could drive a
quality picker later.

### 3.4 A file behind localStorage

The fix was to stop relying on `localStorage` as the source of truth. The desktop app
now backs every `localStorage` entry with a JSON file, `gryt-global.json`, in the
Electron userData directory [5]. That directory survives updates and reinstalls.

On startup, before React even renders, the app loads the file store over IPC and
restores everything into `localStorage`. Then it patches `localStorage.setItem` and
`localStorage.removeItem` so that every future write is synced to the file as it
happens. The file store is the source of truth, and `localStorage` is a fast
in-memory cache in front of it.

On first launch after the update, a one-time migration copies all existing
`localStorage` entries into the file store. If you already had data in
`localStorage`, it's kept. If `localStorage` was empty but the file store had data
from a previous session, it gets restored.

None of the code that reads or writes `localStorage` changed. The theme hook, the auth
module, the token storage and the settings system all call `localStorage.getItem` and
`localStorage.setItem` exactly as before.

## 4 What it costs

These are worked out from the design, not measured.

On the client: nothing. Hardware encoders (NVENC, Quick Sync, AMF) support temporal
SVC natively for VP9, AV1 and H.264. The encoder does the same amount of work whether
SVC is on or off.

On the SFU: parsing the 3-byte Dependency Descriptor header per RTP packet adds
nanoseconds of overhead. The per-receiver fanout replaces one `Write()` call with N
`Write()` calls, but the total I/O is the same. Memory overhead is one lightweight
track object per receiver per video track. In a 10-person room with 2 video tracks,
that's 20 extra objects.

Where SVC actually saves something is downstream bandwidth. Instead of pushing 30 fps
at somebody who can't take it, and causing retransmits and congestion, the SFU sends
each viewer only what they can absorb.

## 5 Discussion

### 5.1 Limitations

- SVC here is temporal only. A viewer on a slow connection gets fewer frames at the
  same resolution.
- H.265/HEVC can't be offered, since WebRTC won't negotiate it.
- The storage bug didn't fail consistently. It could work for weeks and then lose
  everything on the next launch, so the fix couldn't be checked against an on-demand
  reproduction.

### 5.2 Future work

- A quality selector for incoming streams, driven by the `set_layer` event
- Spatial SVC (L2T3, L3T3), for scaling resolution as well as frame rate
- End-to-end encryption with SFrame [6] and insertable streams, which pairs well with
  the per-receiver track model

## 6 Conclusion

**Why did screen sharing load the CPU?** The browser picked VP9, which consumer GPUs
rarely encode. Preferring H.264 moves the work to the GPU, and AV1 is there for
hardware that has it.

**How can one stream serve very different viewers?** By sending three temporal layers
in one stream and letting the SFU forward each viewer only what its bandwidth allows,
so a bad connection no longer sets off keyframes for everyone.

**Why did the desktop app lose its data?** Electron's `localStorage` is tied to an
origin that can change. A file in the userData directory is now the source of truth.
