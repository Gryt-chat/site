**Title:** Inside Gryt's infrastructure: services, trust and self-hosting\
**Date:** 22 February 2026\
**Author:** Sivert Gullberg Hansen\
**Keywords:** architecture, self-hosting, OIDC, JWT, WebRTC, SFU, trust boundaries

## Abstract

Gryt is a set of independent services: a web and desktop client, a signaling server,
an SFU for media, Keycloak for identity, a database and object storage. Each runs in
its own container and can be self-hosted. This post describes how they fit together
and what someone using a Gryt server is trusting. Login goes to a hosted Keycloak at
`auth.gryt.chat` with OIDC and PKCE. Servers only ever see a signed token, which they
check against Keycloak's public keys. Each server then issues its own short-lived
token, scoped to that server and revocable server-wide. Voice is encrypted on the
wire with DTLS-SRTP. Only the client, the server, the SFU's signaling port and its
UDP media range face the network. What you trust is narrow: `auth.gryt.chat` with
your login, and whoever runs the server with your voice, messages and files.

## 1 Introduction

With Discord, Slack, Teams, or any other centralized platform, your identity is owned
by that company. Your username, your email, your profile, your social graph, your
login history: all stored on their servers, governed by their policies, accessible
to their employees, and deletable at their discretion.

Gryt is built differently, and I want to be honest about what it is and isn't. This
post answers two questions:

1. **How do Gryt's services fit together?**
2. **What does someone using a Gryt server have to trust**, and whom?

## 2 Architecture

Each service handles one concern (signaling, media, identity, storage, persistence),
and they talk over well-defined boundaries. Every service runs in its own container,
every connection is authenticated, and every piece of the stack can be self-hosted.

### 2.1 Client

The Gryt client is a React app that ships two ways: as a web app served by Nginx in
Docker, and as an Electron desktop app with auto-updates. The client handles the UI,
audio capture, noise suppression with RNNoise [1], and the WebRTC connection to the
SFU.

The client holds no secrets. Authentication uses OIDC with PKCE [2], a public client
flow where no client secret is needed. The client sends you to the Keycloak instance
at `auth.gryt.chat`, you sign in there, and the client receives a short-lived token.
It never sees or stores your password.

### 2.2 Signaling server

The signaling server is a Node.js app using Socket.IO for real-time WebSocket
communication and Express for REST endpoints. It manages rooms, user presence, chat
messages and file uploads, and coordinates the WebRTC handshake between clients and
the SFU.

Each server instance gets its own ScyllaDB keyspace, so several servers can share a
database with their data kept apart. The server also connects to MinIO for
S3-compatible file storage: avatars, attachments and custom emoji.

### 2.3 SFU

The SFU (Selective Forwarding Unit) is written in Go using the Pion WebRTC library
[3]. Its job is to receive one audio stream from each participant and forward it to
everyone else in the room, as Figure 2 shows. No mixing and no transcoding.

Each client uploads a single audio stream regardless of room size, so a person's
upload stays the same whether there are 2 people in the room or 20.

The SFU talks to the signaling server over an internal WebSocket for room management
and credential validation. It exposes a UDP port range for WebRTC media.

### 2.4 Auth

Gryt uses Keycloak [4], a widely used open-source OIDC/OAuth 2.0 server, as its
identity provider, hosted at `auth.gryt.chat`.

You're **not expected to host Keycloak yourself**. The auth package [5], including
the realm configuration, custom theme and Docker setup, is published purely for
transparency. You can see exactly how the instance is configured, what data it
stores, and how the login theme works.

**The signaling server never sees your password.** It only receives a signed JWT [6]
from Keycloak and verifies the signature against Keycloak's public keys, the JWKS
endpoint. It doesn't need to talk to Keycloak at sign-in time, only to have the
public key set, which it caches.

### 2.5 Database and object storage

Gryt used ScyllaDB, a NoSQL database compatible with the Cassandra query language. It
stored server configuration, user profiles, chat messages, roles and member data.
It has since been replaced by SQLite (see the update at the top).

File uploads (avatars, attachments, custom emoji) are stored in MinIO, an
S3-compatible object store. That keeps binary data out of the database and makes it
easy to swap in any S3-compatible backend: AWS S3, Backblaze B2, Cloudflare R2, or
your own MinIO.

## 3 Security model

### 3.1 Media encryption

All voice is encrypted with DTLS-SRTP [7], which WebRTC requires. The encryption is
set up between the client and the SFU:

1. The client and SFU establish a UDP path via ICE.
2. A DTLS handshake runs over that path to exchange encryption keys.
3. All audio packets after that are encrypted with SRTP.

Each client's DTLS session ends at the SFU. So the SFU decrypts every packet and
encrypts it again for each person it forwards to. Nobody on the network between you
and the SFU can listen, but whoever runs the SFU could. End-to-end encryption on top
of this is future work (Section 5.3).

### 3.2 Token-based authentication

When auth is enabled, every connection goes through two layers of token checks:

1. **Identity.** The client presents a Keycloak-issued JWT. The server verifies the
   signature against the JWKS public keys, and checks the issuer, audience and
   expiry.
2. **Session.** After that, the server issues its own short-lived JWT, signed with
   `JWT_SECRET` and scoped to the specific server host. It carries a `tokenVersion`
   that can be bumped server-wide, for example after a security incident.

```
Authorization: Bearer <server-issued JWT>
├── serverHost: "api.gryt.example.com"  ← scoped to this server
├── tokenVersion: 3                     ← stale tokens are rejected
└── sub: "user-uuid"                    ← identity from Keycloak
```

If a token's `serverHost` doesn't match the current server, it's rejected. If its
`tokenVersion` is behind the server's current version, it's rejected. Both are
checked on every authenticated request.

### 3.3 Network isolation

In the default Docker Compose deployment, services talk over an internal bridge
network. Table 1 lists the only ports exposed to the outside.

**Table 1:** Ports a default deployment exposes.

| Port | Service | Protocol | Purpose |
|------|---------|----------|---------|
| 3666 | Client | TCP | Web UI |
| 5000 | Server | TCP | API + WebSocket |
| 5005 | SFU | TCP | Signaling |
| 10000–10019 | SFU | UDP | WebRTC media |

ScyllaDB and MinIO are **never exposed** to the public network. They only accept
connections from within the Docker network. The SFU's internal WebSocket, used by the
signaling server for room management, also stays internal.

For Cloudflare Tunnel deployments, HTTP services bind to `127.0.0.1`, so they're only
reachable through the tunnel. The UDP ports for WebRTC are the exception, since
Cloudflare Tunnel doesn't carry UDP.

### 3.4 No implicit trust between services

The SFU doesn't accept connections blindly. When a server registers a room with the
SFU, it provides credentials. When a client tries to join, the SFU checks those
credentials before creating a peer connection. If the signaling server goes down, the
SFU cleans up empty rooms after a timeout rather than leaving zombie sessions.

## 4 What you're trusting

By default, Gryt uses the hosted Keycloak at `auth.gryt.chat`, run by me. When you
sign up, your email and password go to that Keycloak instance. So you're trusting me
with those credentials. Table 2 sums up who holds what.

**Table 2:** Who sees what.

| Who | Sees |
|---|---|
| `auth.gryt.chat` (me) | Your email and password |
| Whoever runs the server you join | A verified identity, your messages and files on their disks, and your voice at their SFU |
| Anyone on the network in between | Encrypted traffic only |
| Third parties | Nothing. No analytics, no telemetry, no usage tracking |

A few more things follow from the design:

- **One identity, every server.** You sign up once and your identity works across
  every Gryt server. Server hosts validate your token cryptographically. They don't
  store or manage your credentials.
- **You can use a throwaway email.** The only requirement is that it can receive a
  verification link. Keycloak doesn't care, and neither does Gryt.
- **The auth source is open** [5], so you can audit exactly what's running at
  `auth.gryt.chat`.
- **Nothing phones home.** The only thing that leaves a server is token validation
  against `auth.gryt.chat`.

## 5 Discussion

### 5.1 Deploying it

You should be able to run Gryt anywhere, with whatever infrastructure you're
comfortable with. The stack supports:

- Docker Compose: one command, runs everything on one machine
- Cloudflare Tunnel: TLS with no open ports, except the SFU's UDP
- A reverse proxy: Caddy, Nginx or Traefik with automatic TLS
- Kubernetes: a Helm chart with ingress, security contexts and resource limits

The whole stack starts with a single `docker compose up -d`. No build step, no
compilation, no dependency installation. Pre-built images are published to GHCR on
every release.

### 5.2 Limitations

- **Sign-in is central.** Every server points at `auth.gryt.chat`, because that's what
  makes "sign up once, join any server" work. Self-hosting Keycloak is possible, and
  the code and theme are in the repo, but it isn't expected, and documentation for it
  is still planned.
- **The SFU can hear the call**, as Section 3.1 says.
- **The stack has moved on.** The database is SQLite now, so Section 2.5 and Figure 1
  describe the stack as it was in February 2026.

### 5.3 Future work

End-to-end encryption for voice, so the SFU forwards audio it can't read, and
documentation for running your own Keycloak.

## 6 Conclusion

**How do the services fit together?** A client, a signaling server and an SFU, with
identity, data and files in services of their own. Each runs in its own container and
can be self-hosted, and only four ports face the network.

**What do you have to trust?** `auth.gryt.chat` with your login, and the person
running the server with your voice, messages and files. Server hosts never see your
password, and nothing goes to third parties. You can use a throwaway email if you'd
rather not hand over your real one.

If you want to set up your own instance, check the
[deployment guide](https://docs.gryt.chat/docs/host/docker-compose). If you want to
dig into the source, everything is on [GitHub](https://github.com/Gryt-chat/gryt)
under AGPL-3.0. Questions? Come chat on [our Gryt server](https://gryt.chat/community)
or [Discord](https://gryt.chat/discord).
